# Redis-backed ephemeral authentication state

Status: **infrastructure available; production OTP cutover not enabled**.

The existing PostgreSQL OTP store remains isolated and unexposed. Do not remove migration 032 or switch authentication before the Redis adapter, integration tests, rate limits and SMS delivery are complete.

## Responsibilities

- PostgreSQL: authoritative user accounts, verified contact details, capabilities, and durable security/audit records.
- Kratos: identity credentials and authentication sessions.
- Redis: expiring OTP challenge payloads, attempt counters, resend cooldowns, per-source and per-phone rate limits, and short-lived verification tokens.
- SMS provider: out-of-band code delivery. Never send codes in API responses or store them in logs.

## Docker and operations

The local `docker-compose.yml` includes a private `redis:7.4-alpine` container and exposes `REDIS_URL=redis://redis:6379/0` inside the Go API container. Redis is not published to the host.

Redis uses a 128 MB memory limit with `noeviction`, and RDB/AOF persistence is deliberately disabled. If memory is exhausted, OTP issuance must **fail closed**, not silently drop a security record. An outage can invalidate in-flight OTPs; users may initiate a new verification after service restoration. Live identity sessions stay with Kratos, not Redis.

For production, configure an authenticated private Redis endpoint with TLS, network isolation, monitored memory headroom, and a separately provisioned secret for HMAC keying. The local no-password container is **not production configuration**.

## Required implementation before activation

- Redis operations for issue, deduplicate, verify and consume must be **atomic** across all API replicas (Lua scripts or equivalent).
- Challenge and verification token keys have explicit TTL. Never rely on a client cleanup job to expire them.
- The six-digit OTP is generated by crypto/rand; Redis stores only a challenge-specific keyed HMAC digest and limited metadata. Phone identity in cache keys must be protected against trivial enumeration.
- Issue retries with the same idempotency key return the same challenge and **do not send another SMS**. A different key during cooldown must not bypass the cooldown.
- Rate limits by requester IP, phone and purpose apply *before* any SMS send; limits are server-authoritative, with bounded Retry-After. Do not trust spoofed client headers.
- Wrong code attempts decrement a durable-for-the-TTL budget; a correct code after the maximum attempts is rejected. Single-use completion must remain valid under concurrent calls.
- Successful OTP completion produces a short-lived, single-use proof bound to phone and purpose, not a full authenticated session.
- SMS delivery must have defined failure/retry semantics so an issued challenge cannot silently trigger multiple SMS sends.
- CI tests should run against a disposable Redis instance for expiry, attempts, concurrency, idempotency, cooldown, rate limiting and Redis-unavailable behavior.
- Flutter must avoid polling and duplicate in-flight requests; backend validation and rate limits remain authoritative.

## Operator commands

```sh
docker compose up -d redis
docker compose ps redis
docker compose exec redis redis-cli ping
```

Expected ping: `PONG`. Do not publish port 6379.
